# popups · 二级弹层(可选能力,默认不做)

看板的默认形态是**纯展示**:数据画在带区上,用户只看不点。这一篇讲的是可选的进阶形态——点某一块弹出一个小窗看明细或就地操作。

**先说清楚:大多数板不需要这个。** 弹层带来的不是"多一个功能",而是多一套状态(哪个开着、盖在谁上面、什么时候关),这套状态 Rainmeter 会**持久化**,出问题的方式很隐蔽。没有真实的下钻需求就别做——纯展示板永远是更稳的那个。

## 0. 判据:你需不需要弹层

| 情形 | 结论 |
|---|---|
| 每块 3~4 行以内,一屏看得完 | **不做**。信息全摆在带区上,点都不用点 |
| 只是"想让它更像 app" | **不做**。这是形态偏好,不是需求;代价是下面整篇的复杂度 |
| 用户只在早上瞥一眼,不操作 | **不做** |
| 某块的条目天然多于能显示的行数(待办 20 条只显示 4 条) | 可做:弹层给"完整列表" |
| 需要看某条的详情(留言全文、报错堆栈) | 可做:弹层给"这一条的明细" |
| 需要就地操作(标记已读、勾完成、改一条) | 可做,但先想想能不能用带区上的单击热区解决 |

做之前跟用户说一句人话:"要不要点开看详情?不点开的话,这块就只显示前 4 条,更省事也更不容易坏。"给单一推荐,别列菜单。

## 1. 🔴 激活态是持久化的——最贵的一条

Rainmeter 把"哪些 config 现在是开着的"记在 `%APPDATA%\Rainmeter\Rainmeter.ini` 里:

```ini
[Deskdash\Detail]
Active=1
```

而 `!RefreshApp`(部署脚本每次都发)会**重扫注册所有 config 并重新加载每一个 Active=1 的**。两件事凑一起的后果是:

> **只要有过一次"意外激活",这个弹层就会在之后每一次部署里自己冒出来,用户关掉也没用。**

真实事故:部署脚本为了让弹层的 `@Include` 文件存在,调了一条名叫"显示这一类内容"的命令去生成文件——那条命令的收尾是 `!ActivateConfig`。于是每部署一次,用户桌面上就多一个弹窗;关掉,下次部署又回来,连着几天都以为是"关不掉"。**"关不掉"是持久化状态的特征,不是手滑的特征**;听到用户说"又回来了/一直消不掉",第一件事是去 `Rainmeter.ini` 看 `Active`,而不是在触发点上找谁点了它。

三条据此写死的规则:

1. **"产出文件"和"打开界面"必须是两条命令。** 一条命令如果既写文件又动界面,调用方就没有办法只要前者。给它一个只落盘、一个 bang 都不发的形态(例如 `--render-only`),部署链路只准调这一个。
2. **部署收尾显式关闭所有弹层。** 光"不主动打开"不够——上一次遗留的 `Active=1` 会被这一轮 `!RefreshApp` 原样拉回来。收尾对每个弹层 config 发一次 `!DeactivateConfig`,把那条记录一并清掉。部署是后台维护,跑完桌面上不该多出任何一个窗。
3. **判据看 `Rainmeter.ini` 的 `Active` 字段,不看截图。** 截图只能证明"此刻没有",证明不了"以后不会再来"。

## 2. 层级:三条配套,单独调一条必翻车

弹层要比看板高,但**不该比用户正在用的软件高**。Rainmeter 的 `AlwaysOnTop` / `!ZPos` 只有四档,各有代价:

| 值 | 含义 | 代价 |
|---|---|---|
| `-2` | 贴在桌面上 | 按 Win+D 显示桌面时**仍然可见**(这通常是看板想要的) |
| `-1` | 窗口层最底 | Win+D 会把它一起藏掉 |
| `0` | 普通窗口 | 会被别的窗口正常遮挡——**这正是弹层要的** |
| `1` / `2` | 置顶 | 一直压在用户正在用的软件前面,点别的窗口也不让位。用户会烦 |

配套写法(缺一条就会复发):

- **看板固定在自己那一档**(常见是 `-2`);
- **弹层一律 `0`**。🔴 绝不能给弹层发 `-2`——那会把它按到看板底下,用户点开的窗直接"沉下去看不见";也别用 `1`/`2`,那是霸屏。弹层只需要比看板高,而看板在桌面层,普通窗口天然就在它上面;
- **刷过看板之后要补一次层级收尾**。桌面层皮肤每次 `!Refresh` 都会重新插一次位置,那一瞬间可能插到别的窗口**前面**;紧接着发的 `!ZPos` 会被刷新本身盖掉,**隔约 0.4~0.5 秒再发才生效**。

还有一条反直觉的:**同层内把 `!ZPos` 发成相同的值是空操作,抬不动窗口**。看板刷新后如果把开着的弹层压住了,要抬它得 `!Refresh` 弹层自己(重建窗口,自然落到本层最前),而不是再发一次 `!ZPos 0`。

**把这套规则收在一个地方。** 散在各处写(采集脚本一份、部署脚本一份、交互脚本一份)必然漂:改好一处,另一处照旧,同一个 bug 换个入口就复发。给"通知 Rainmeter"这件事留唯一入口,层级规则只写一份。

## 3. 关闭要有终点

带操作的弹层(标记已读、逐条处理)要想清楚"点到最后会怎样"。没有终点的话,最后一条处理完窗还杵在那儿,用户看着就像没生效。

同时把两种数字分开,别混:

- **服务端/源头的状态数**(待处理 3 条)——只有在源头真处理了才会变,本地点"已读"不该让它减;
- **本地的"我看过了"标记**——作用范围仅限自家那条提醒流。

两者口径不一致会出这种事:带区上写"未处理 2",点进去却是空的——数字取的是源头总数,列表却又套了一遍本地已读过滤。**一个数字和它的下钻列表必须同源**;"已读"只允许作用在提醒流上。

## 4. 测试和部署都不许替用户点

被测软件就装在本机时,"发命令"这一层没打桩**就是真的发出去了**。曾经跑一次测试就在用户桌面上弹一个窗——测试全绿,因为副作用不在任何断言里。

在测试根 `conftest.py` 放一个 autouse 的全局桩,别指望每个用例自己记得打桩(漏一个就是真机上多一个窗):

```python
@pytest.fixture(autouse=True)
def _never_touch_the_real_desktop(monkeypatch):
    from lib import skin_bus          # 你那个「通知 Rainmeter」的唯一入口
    monkeypatch.setattr(skin_bus, "subprocess", _NoProcess)   # 换名字,不是改属性
```

🔴 **换掉的必须是模块里那个名字(`skin_bus.subprocess`),不是 `subprocess.run` 这个属性。** 后者改的是全局模块对象,整个进程里所有人的 subprocess 都被换掉,别的用例会当场 `'NoneType' object has no attribute 'stdout'`。

桩下在 subprocess 这一层(而不是更上面的 `notify`),好处是用例仍可以自己再 patch 一次 `skin_bus.subprocess.run` 去**记录**发了哪些 bang——autouse 先生效、用例后生效,后者赢,既拿得到记录又永远落不到真进程上。真要测这几个函数本身的用例用 marker 单独放行。
